Inverse Pandya MPI 方案对比

对比当前 output-driven inverse Pandya 路径和计划中的 cc-channel-driven scatter 路径。 核心问题是：Z_bar(ch_cc) 由 cross-coupled channel owner 生成，但最终 Z.TwoBody(ch, ch) 必须由 ordinary two-body channel owner 写入。

旧版本

普通输出 channel 驱动

每个 rank 在 inverse Pandya 阶段遍历普通 Z(ch, ibra, iket) 空间， 只使用自己拥有的 ch_cc 对该输出元素的部分贡献，然后发送给 TwoBodyChannelOwner(ch)。

1. 计算本 rank 拥有的 cc blocks Z_bar[ch_cc] 只在 CrossCoupledChannelOwner(ch_cc) 上生成。
↓
2. 扫所有普通输出元素 遍历 ch, ibra, iket，在角动量循环中筛选本 rank 拥有的 ch_cc。
↓
3. 形成 partial zijkl 同一输出元素在本 rank 上先局部求和。
↓
4. 发送给普通 channel owner 通过 Alltoallv 发送 (ch, ibra, iket, value)。
新版本

cc channel scatter 驱动

每个 rank 只处理自己拥有的 ch_cc。根据预先构造的 inverse Pandya plan， 直接把 Z_bar[ch_cc] 的贡献 scatter 到普通 Z(ch, ibra, iket) owner。

1. 计算本 rank 拥有的 cc blocks 与旧版本一致，仍按 CrossCoupledChannelOwner(ch_cc) 构造 Z_bar。
↓
2. 查 inverse plan 对每个 ch_cc，读取它会贡献到哪些 ch, ibra, iket。
↓
3. 生成 contribution events 计算 delta = coeff * Zbar(row_cc, col_cc)，按目标 rank 分桶。
↓
4. 本地合并后发送 先按 (ch, ibra, iket) 求和，再通过 Alltoallv 发给 owner。

详细对比

维度 旧版本：output-driven 新版本：cc-scatter-driven
自然工作单元 普通 two-body 输出元素 Z(ch, ibra, iket) cross-coupled channel Z_bar(ch_cc)
主循环 扫所有普通 ch、ibra、iket 扫本 rank 拥有的 ch_cc 以及对应 scatter plan
owner 关系 ch_cc owner 负责部分求和，ch owner 最终写入 ch_cc owner 生产事件，ch owner 接收并合并写入
重复扫描 较多。多个 rank 都会扫普通输出空间，只是筛掉非本 rank 的 ch_cc 较少。每个 rank 只处理自己拥有的 cc channel plan
局部性 围绕普通输出元素组织，对 Z_bar[ch_cc] 的访问较分散 围绕单个 Z_bar[ch_cc] 连续消费，缓存局部性更好
通信粒度 本 rank 已经把同一输出元素的部分贡献局部合成一个 zijkl 如果不合并会产生更多小贡献，必须做本地排序求和
额外内存 较低，不需要 inverse plan 较高，需要 inverse_plan_by_cc 或可重建的轻量 plan
实现风险 低。公式路径贴近现有实现 中高。必须严格处理 phase、norm、Hermitian、重复计数和 batch 过滤
可扩展性 rank 增加后，普通空间重复扫描成本更明显 更适合大模型空间和多 rank，因为工作天然按 cc channel 分布
适合阶段 作为正确性基线和第一阶段 typed communication 重构 作为性能优化路径，通过环境变量与旧路径并行验证
旧版本伪代码 
for ch in ordinary_channels:
  for ibra in channel_kets(ch):
    for iket in upper_triangle(ch):
      zijkl = 0

      for Jprime in allowed_inverse_pandya_terms:
        ch_cc = get_cc_channel(Jprime, ...)

        if owns_cross_coupled_channel(ch_cc):
          zijkl += coeff * Zbar[ch_cc](row_cc, col_cc)

      owner = TwoBodyChannelOwner(ch)
      send_buffer[owner].push(ch, ibra, iket, zijkl)

received = Alltoallv(send_buffer)
for c in received:
  Z(ch)(ibra, iket) += c.value
新版本伪代码 
for ch_cc in owned_cross_coupled_channels:
  Zbar_ch = build_Zbar(ch_cc)

  for p in inverse_plan_by_cc[ch_cc]:
    dz = p.coeff * Zbar_ch(p.row_cc, p.col_cc)

    if abs(dz) < cutoff:
      continue

    owner = TwoBodyChannelOwner(p.ch)
    thread_buffer[tid][owner].push(p.ch, p.ibra, p.iket, dz)

local_merge_by_key(thread_buffer)
received = Alltoallv(send_buffer)
remote_merge_by_key(received)
apply_to_Z(received)

关键注意事项

新版本只有在加入本地合并后才值得做。否则 ch_cc scatter 会产生大量细碎 (ch, ibra, iket, value) 事件，把旧版本节省下来的扫描成本转移成通信成本。

推荐迁移路线

  1. 先把旧路径的四个 double 包改成 typed TwoBodyContribution。
  2. 保持旧算法不变，验证 MPI 与非 MPI、单 rank 与多 rank 结果一致。
  3. 从现有 inverse Pandya 循环抽取 inverse_plan_by_cc。
  4. 加入 cc_scatter 路径，用环境变量切换。
  5. 比较 Z.TwoBody 差异、Alltoallv 数据量、最大 peer 负载和 wall time。

建议开关

IMSRG_MPI_PANDYA_INVERSE=output
IMSRG_MPI_PANDYA_INVERSE=cc_scatter
IMSRG_MPI_PANDYA_CC_BATCH=4

output 保留当前路径作为基线； cc_scatter 启用新路径； batch size 继续控制每次持有的 Z_bar(ch_cc) 数量。
